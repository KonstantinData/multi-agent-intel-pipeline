# Phase 2 Storage Architecture: Hetzner/Postgres/pgvector + Cloudflare

Schema version: `2026-05-12.1`

## Scope

This document is the alignment artifact for TODO point 3 and the storage side
of point 4. It defines the production backbone without making the local MVP
dependent on Postgres.

## Roles

Hetzner is the primary compute and data-residency location for the Python
runtime, PostgreSQL, pgvector, run state, checkpoints, and process memory.

Cloudflare is the public edge: DNS, TLS, WAF, DDoS protection, rate limiting,
Access/Zero Trust, and Tunnel. Cloudflare Workers may be used only as a thin
gateway/status/webhook layer. Long-running AG2 orchestration stays on Hetzner.

Cloudflare R2 is optional object storage for large reports/exports. PostgreSQL
stores only metadata, storage keys, hashes, and small JSONB state.

## Schema Boundary

Run-specific state:
- `runs`
- `run_checkpoints`
- `run_events`
- `run_artifacts`
- `run_locks`

Long-term process memory:
- `memory_patterns`
- `memory_retrieval_events`
- `memory_backfill_jobs`

Point 3 owns schema, storage contracts, migration and operational behavior.
Point 4 owns retrieval context, ranking, policy gates and selected pattern
semantics.

## IDs And Versions

- `run_id`: existing sortable UTC id.
- `pattern_id`: UUID generated by Postgres.
- `schema_version`: currently `2026-05-12.1`.
- `embedding_model`: persisted per pattern because vector dimensions and model
  quality may change.
- `retrieval_policy_version`: persisted per retrieval event for replay.

## JSONB Vs Indexed Columns

Indexed columns are used for state transitions and filters:
- run status, current phase, normalized domain, timestamps
- pattern role, scope, industry hint, schema version, content hash
- retrieval run id, role, policy version

JSONB is used for snapshots and flexible payloads:
- `run_context_snapshot`
- `content_json`
- event content
- artifact metadata
- retrieval metadata

Every JSONB payload must include or be adjacent to `schema_version`.

## Failure Policy

Production profile:
- missing Postgres DSN: block run start with `postgres_dsn_missing`.
- DB unavailable: block run start or fail current phase; do not silently fall
  back to file memory.
- pgvector unavailable: memory retrieval can degrade only if explicitly
  configured; the degradation must be recorded.
- object storage unavailable: block report/export, preserve run state.
- backfill failure: no impact on running customer runs.

Local development profile:
- local JSON artifacts and `FileLongTermMemoryStore` remain supported.
- local files are not the production system of record.

## Migration Strategy

1. Freeze schema and apply `20260512_phase2_storage.sql` to a test Postgres
   instance with pgvector.
2. Dry-run migration from `artifacts/memory/long_term_memory.json`.
3. Re-run scrubbing for every candidate pattern.
4. Insert by stable `content_hash`; duplicates update score/metadata only when
   replacement rules allow.
5. Dry-run run-artifact migration from `artifacts/runs/*`.
6. Enable production profile only after health checks pass.

Rollback:
- keep local artifacts read-only until production follow-up and export paths are
  verified.
- schema changes must be additive until a new schema version is active.

## Security And Data Policy

Long-term process memory must never store target company domains, URLs, email
addresses, person names, legal company names, or concrete run conclusions as
reusable truth.

Run brain remains customer/run specific and is subject to retention/deletion.
Scrubbed process memory may remain after removing `source_run_id` linkage when
required by retention policy.

## Observability

- `storage.run.create`
- `storage.checkpoint.write`
- `memory.retrieve`
- `memory.pattern.write`
- `memory.backfill_job`

Required fields:
- `run_id`
- `component`
- `phase`
- `status`
- `error_code`
- `duration_ms`
- `schema_version`
- optional Cloudflare request id / correlation id
