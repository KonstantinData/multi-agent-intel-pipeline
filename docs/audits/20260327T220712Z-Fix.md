## ✅ RF3-1 — `product_asset_scope` Regression

**Severity:** hoch  
**Status:** ✅ Erledigt

**Umsetzung:**
- `lead.py` / Lead-Prompt (Fix A): Retry-Logik differenziert jetzt zwischen Core-Failures und Supporting-Failures. Supporting-only-Rejections (`core_passed == core_total` aber `approved=false`) loesen keinen Retry aus. Budget-Disziplin-Abschnitt ergaenzt: maximal 2 Retries pro Task, alle Tasks mit Gaps abschliessen ist besser als wenige Tasks perfekt.
- `lead.py` / `finalize_package` UND `_build_fallback_package` (Fix C): Wenn `product_asset_scope` leer ist nach allen Tasks, wird `products_and_services` aus `current_payload` als Fallback mit " — classification pending" Annotation uebernommen. Safety-Net in beiden Package-Pfaden.

### Diagnose (aus run_context.json)

CompanyDepartment Artifact-Registry:
- `company_fundamentals`: 1 Attempt ✅
- `economic_commercial_situation`: **4 Attempts** (rejected wegen fehlender `inventory_signals`)
- `product_asset_scope`: **0 Attempts** — nie ausgefuehrt

`max_round = len(assignments) * 15 = 3 * 15 = 45`. Aber `economic_commercial_situation` hat ~24 Runden verbraucht (4 Attempts × ~6 Runden pro Cycle: run_research → review_research → Lead-Entscheidung → retry). Plus `company_fundamentals` ~8 Runden = ~32 Runden. Dann bleiben ~13 Runden, und der Lead braucht noch Text-Turns fuer die Finalisierung → `product_asset_scope` kommt nie dran.

### Root Cause

Zwei zusammenwirkende Probleme:

**1. `economic_commercial_situation` wird endlos retried wegen `inventory_signals`.**

Die Validation-Rule in `use_cases.py`:
```
{"check": "min_items", "field": "economic_situation.inventory_signals", "value": 1, "class": "supporting"}
```

Die Rule ist `supporting` (nicht `core`), also sollte sie den Task nicht blockieren. **Aber:** der Critic in `critic.py` setzt `approved = False` wenn `evidence_strength == "weak"` — und `evidence_strength` ist `"weak"` wenn keine externen Quellen vorhanden sind. Das passiert weil die `economic_commercial_situation` Queries (`"ZF" revenue`, `"ZF" restructuring`) zwar Ergebnisse liefern, aber die Quellen als `"owned"` oder ohne URL klassifiziert werden.

Der Lead sieht `approved=false` und retried — obwohl alle `core` Rules bestanden haben. Der Lead-Prompt sagt: "REJECTED (approved=false, attempt=1) → retry". Er unterscheidet nicht zwischen "core failed" und "supporting failed + weak evidence".

**2. Kein Rundenbudget-Schutz pro Task.**

Es gibt keinen Mechanismus der verhindert, dass ein einzelner Task das gesamte Rundenbudget aufbraucht. Wenn ein Task 4× retried wird, bleiben fuer die restlichen Tasks keine Runden uebrig.

### Patch-Sequenz

**Fix A — Lead-Prompt: Retry nur bei Core-Failures (empfohlen, schnell)**

`lead.py` / `_lead_system_prompt`: Den Retry-Abschnitt aendern:
- Aktuell: "REJECTED (approved=false, attempt=1) → retry"
- Neu: "REJECTED with core failures (core_passed < core_total) → retry. REJECTED with only supporting failures (core_passed == core_total but approved=false) → accept with documented gaps, move to next task."

Das verhindert, dass der Lead endlos retried wenn nur `supporting` Rules fehlschlagen.

**Fix B — `already_completed` Guard: Revision nur bei explizitem Request (defensiv)**

`lead.py` / `run_research`: Der `already_completed` Guard prueft `task_key not in run_state.revision_requests`. Aber der Lead setzt `revision_requests` nicht explizit — er sagt einfach "run_research again". Das bedeutet der Guard greift nicht bei Retries.

Fix: Wenn ein Task bereits ein Artifact hat und kein expliziter `revision_request` vorliegt, sollte `run_research` den Task nicht erneut ausfuehren sondern `already_completed` zurueckgeben. Das begrenzt Retries auf Faelle wo der Lead bewusst eine Revision anfordert.

**Fix C — Fallback-Package: product_asset_scope aus current_payload befuellen (Sicherheitsnetz)**

`lead.py` / `_build_fallback_package` und `finalize_package`: Wenn ein Task 0 Attempts hat (nie ausgefuehrt), sollte der Fallback-Pfad pruefen ob `current_payload` bereits Daten enthaelt die als Fallback genutzt werden koennen. Fuer `product_asset_scope` koennte `products_and_services` aus dem `current_payload` als Fallback dienen — analog zur RF-4 Bridge im Worker.
